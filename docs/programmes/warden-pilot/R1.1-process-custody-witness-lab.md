# Warden Pilot R1.1 — Separate-Process Synthetic Custody and Effect Witness

**Status: DEVELOPMENT EXPERIMENT — NOT AN INDEPENDENT RIVER SERVICE. APPLICATIONS, BOOKINGS, RECRUITMENT AND LIVE EXECUTION REMAIN ON HOLD.**

This proposed release extends R1.0's same-process, two-database demonstration with two separate Node.js child processes: **a custody reservation process** and **a read-only local effect witness process**. It is intended to falsify incorrect assurances that a custody receipt alone proves delivery.

## Implementation
- `scripts/warden-r11-custody-worker.mjs` runs only as a child process when its synthetic lab role is explicitly set to `custody` or `witness`.
- The test parent provisions two fixture processes using `child_process.fork`, transfers public signing verification keys over Node IPC, and simulates a local provider registry write with the established R0.9 lab.
- The **custody worker** validates an Ed25519-signed, short-lived, synthetic `candidate:create` grant; reserves a one-time `jti`, tenant, candidate and digest in its own SQLite database; verifies a signed witness receipt; and only then records `COMMITTED_OBSERVED`.
- The **witness worker** opens the candidate SQLite database **read-only**. It validates the pinned custody signature, tenant, candidate, subject and expected digest, then independently reads the owner, stored candidate payload and status from the other process's durable registry and signs `OBSERVED_LOCAL`.
- The **test parent** checks both signed receipts and the persisted custody head after a simulated lost ACK. It never retries an ambiguous effect.
- Tests include absent or mismatched local effects, untrusted/forged acknowledgment, wrong scope, revocation before commit, process restart with nonpersistent keys, and attempts to use administrative worker operations for billing or licencing.

## Exact evidence boundary
The result is a **same-host observation by a separate Node process**, not an external provider acknowledgment or independent River receipt. A test parent's access to fixture keys and IPC channels is not adequate trust separation. Local filesystem permissions and process identity are **not separated** by this code. Reuse or reboot of a custodian changes its ephemeral signing key, making earlier receipts untrusted to the restarted process and causing a deliberate HOLD. Persistent signing keys, independent host/UID confinement, revocation distribution and stable trust roots are absent.

The custody worker enforces local replay protection as long as its custody SQLite store survives. An operator with write access to that database can delete the record, and the system is not capable of independently detecting all such omissions without externally anchored evidence.

The read-only witness verifies that an example registry row *presently* matches the reserved effect. It does not prove the external customer service occurred, does not attest the business/legal identity of a pilot partner, and cannot certify an arbitrary external provider outcome. The provider and witness share the same host, filesystem and (in this lab) OS identity.

## Required independent evidence before any production claim
1. **Independent custodian:** separate OS identity/host, inaccessible signing material, policy-protected immutable/append-only records, independent operator and incident response, authenticated local/network channel.
2. **Persistent trust:** authenticated identity-to-company membership and tenant binding, key rotation/revocation, monotonic trusted clock, anti-replay after restart and network outage.
3. **True provider effect:** provider-owned operation ID, deterministic idempotency, signed status/result proof, bounded source-of-truth reconciliation and handling of post-commit acknowledgment loss.
4. **Independent River evidence:** externally anchored head, complete record and omission detection, custody chain and verifiable signer/sequence linkage.
5. **Commercial and privacy:** authorized rights holder/pilot grantor, data controller, secure real applicant intake and notice, permitted Esomoire data visibility, partnership contracts, tax and legal review.
6. **Release chain:** existing draft dependencies #5 → #6 → #8 → #9 → #10 → #11 → this R1.1 proposal; Commons Vercel/project ownership must be verified.

**All ten R0.7 live pilot gates remain HOLD.** No live identity, production registry, applicant details, private customer records, product licence, booking calendar, invoice, payment or Warden execution has been activated. The child processes execute only inside GitHub CI/local synthetic tests, not as deployed services.
