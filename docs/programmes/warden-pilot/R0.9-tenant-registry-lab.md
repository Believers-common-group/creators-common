# Creators Common — Warden pilot R0.9 local tenant-isolation and signed-grant lab

**Release position: OFFLINE SYNTHETIC LAB ONLY — NOT A LIVE APPLICATION SERVICE.**

This next tranche tests one narrowly scoped technical prerequisite for future Esomoire administration. It **does not** turn the R0.8 static programme into a dynamic application or connect a login provider.

## What was built

- `lib/programs/warden-pilot-r09-lab.ts`: in-process Node.js 24 lab using the built-in `node:sqlite` synchronous API.
- Test-issued, short-lived Ed25519 **synthetic grants** with a caller-supplied trusted verifier key.
- Signed claims bind issuer, audience, synthetic subject, tenant, **individual candidate reference**, role, action, single-use `jti`, issue time and expiry.
- Application recording in a durable **local lab** SQLite file (or memory), compound `(tenant, candidate)` key, per-owner reads, Esomoire administrative reference-only projection.
- Mutation replay token consumption and create/withdraw/audit writes in a single `BEGIN IMMEDIATE` transaction. Per-tenant local digest chain aids *detection of casual modification*, without furnishing independent custody.
- All candidacy and participation remains synthetic, with no financial authority, licence, bookings or Warden execution.
- Multiple negative tests for tampering, unsigned/malformed claims, role confusion, cross-owner/tenant resource reads, double submission, replay after restart, withdrawal and SQLite-storage manipulation.

## Roles

| Actor | Lab permissions | Denied |
|---|---|---|
| Synthetic pilot provider | Create its synthetic candidate, read its own synthetic record, withdraw its own record | Read other owners, other tenants, grant product licences, publish, book, charge |
| Synthetic Esomoire administrator | Read linked `registry`, `listing` and `booking` references for **one resource explicitly authorized in a signed grant** | Read full application/proposal/company information through the admin method; write, approve, contract, invoice, receive payment |
| Untrusted/expired subject | None | Everything |
| Real applicants or real customers | None; the lab refuses their submission | Live data collection |

**Esomoire receives no assumed transaction participation.** Administrative references remain distinct from the independent pilot provider's customer contract/invoice. The lab's registry is not Genesis; the lab grant is **not DigitalMe, Warden or legally authenticated identity**. To use real identities would require the appropriate separately admitted authoritative integration.

## Pilot information boundary

The R0.8 synthetic application still has the same Warden + VSR + DigitalMe proposed defaults; four technology/production conditions; independent third-party roles; and prohibition on offering Quantum Room before hardware validation.

No live intake endpoint, route handler, browser form, database connector, public listing, customer-privacy controller, WebAuthn service, credential issuance, provider invitation, payment processor, booking calendar or live ARK execution is included.

## Assurance limits (important)

1. **Synthetic grant only:** The tests can generate their own local signing keys and confirm Ed25519 validation, but this is not real applicant login, corporate representation proof, protected key custody or revocation checking.
2. **Tenant isolation is application-level:** The lab's SQLite data is readable/mutable by the local process/OS user. There is no RLS, database user separation or externally operated custodian. Caller-supplied `tenant` remains an asserted field in a signed lab token, not a verified organization.
3. **Local replay state is removable:** A test deliberately shows that someone who can write to the SQLite file can delete all tables' history and replay a previously consumed synthetic grant. Local digest chains cannot detect full deletion without an externally anchored head.
4. **Single-process transaction only:** SQLite claims and writes are atomic inside this local file; nothing links them atomically with provider side-effects, independently operated River, customer billing or external services. Not an exactly-once guarantee.
5. **Stored data is intentionally fictional:** No real company PAN/GST, personal details, contact email, customer file or credentials should enter this repository or lab.
6. **Synthetic SQLite filename guard is not confinement:** It discourages accidental use of regular production database names but is not a sandbox, filesystem access-control mechanism, trusted file picker, or defense against a malicious runtime.
7. **No deployable runtime:** Node SQLite runs only in the test/diagnostic environment; the site remains a static Next.js export. No server-side intake/authentication functionality is added to the public pages.
8. **No local audit-to-River assertion:** The lab hash chain is neither signed by independent River nor remotely acknowledged.

These limits require **PRODUCTION HOLD** even if CI passes.
