# Warden Pilot R1.0 — Synthetic Split-Custody Assurance Lab

**Status: REVIEW-ONLY; production/partner intake/action authority remain HOLD.**

This review increment addresses R0.9's demonstrated failure: a writer with local SQLite access could erase local replay records and replay a consumed synthetic registration grant. The R1.0 proposal experiments with **a separate custody database and independent fixture signing key**, but both remain callable within the same Node.js process on one host. No externally operated River custodian, real identity provider, production tenant store or network isolation is established.

## Implemented capability

- `lib/programs/warden-pilot-r10-custody.ts`: separate `node:sqlite` custody fixture, Ed25519-signed detached receipts for `RESERVED` and `COMMITTED` synthetic candidate intentions, and test-only subject revocations.
- `tests/warden-pilot-r10-custody.test.ts`: exact scope/role checking, replay/duplicate reservation, tenant separation, store reopening, tampering, custody outage, revocation before commit, simulated crashes and loss of post-commit acknowledgment.
- Existing R0.9 local registry and R0.8 Esomoire read-only reference projection remain unchanged. Warden, Genesis, River, DigitalMe and Synnergyze are not impersonated as live services.

## Ordered synthetic demonstration

1. Verify a short-lived signed fixture grant bound to example-only tenant, subject, specific candidate, action and JTI.
2. In an independent local fixture database, **reserve** one candidate/effect hash and persist the JTI. If custody is unavailable, deny before any local write.
3. In the R0.9 synthetic registry database, perform the example-only local write with its own independent replay checks.
4. Mark the custody reservation `COMMITTED` and issue a signed fixture receipt. If the acknowledgment is lost, report **HOLD_UNRECONCILED** instead of redoing the operation.
5. For a crash before custody commit or an ambiguous response after commit, retrieve the current signed fixture custody head for **manual review only**. Recovery introspection never automatically replays the effect.

The custody fixture stores only tenant/candidate/subject/JTI/effect digest/state and synthetic revocation identifiers. It has no customer contracts, names, invoices, currency, money movement or billing authority. Administrative Esomoire records remain the limited registry/listing/booking *references* described in R0.8, without customer transaction visibility.

## Explicitly demonstrated limitations

| Observation | Proper interpretation |
| --- | --- |
| Local applicant database deleted, custody database preserved | Earlier grant and even a new JTI cannot re-reserve the same candidate within that tenant while custody history survives |
| Custody record deleted, previously held signed receipt available | Local verifier detects mismatch or missing record; require HOLD |
| Custody record deleted with local receipts also lost | Prior reservation can be issued again: **no externally anchored immutable history** |
| Post-commit response lost | Custody state can be fetched from the synthetic fixture, but remains HOLD pending independent reconciliation |
| Subject revoked after reservation, before commit | Custodian blocks commit; uncommitted local data may already exist, and no compensating action is assumed |
| Custody commit accepted without a local registry write | Signed custody receipt alone is **not proof that the effect occurred** |
| Fixture's keypair generated inside test process | Not trusted production key custody, revocation infrastructure, operator separation or legal identity |

**A compromised same-host operator or process with access to both stores and signing material defeats this proposed lab.** Signatures show fixture-key possession, not external River evidence.
